# 工具卡片（toolview）设计：从「一行日志」到「活动卡片」

> 状态：设计稿 + 可交互 demo v2（`design/toolview-demo.html`）。P0 未实现，先评审。
> 交互稿截图：[确认门 + 桌面 HUD](design/screenshots/demo-hud-gate.jpg)、[失败与恢复 + HUD 需要处理](design/screenshots/demo-hud-failure.jpg)、[接管 + HUD 等你操作](design/screenshots/demo-hud-takeover.jpg)。
> m08916 拍板结论已并入本文（见 §7），HUD 作为 P2 概念的可行性评估见 §9。

## 1. 为什么做

现在的卡片（`client/client.js`）是「一行日志」：工具名 + 一句摘要，展开看参数/输出。
对非技术用户来说，这仍然是黑盒——**操作前不知道要动哪里，操作中看不到进展，失败后不知道该怪谁、下一步做什么。**

DSH 的 `tool.call.toolview` 已按 wire 工具名分发自定义视图，客户端可以先吃下这件事，不改宿主、不改 wire 协议。

目标（按用户 m08806）：

- 第 **n/N** 步：让「做到哪了」一眼可见；
- 目标 **App › 窗口 › 控件**：让用户能判断「点得对不对」；
- **耗时**：知道是快结束了还是卡住了；
- **缩略截图**：比「已点击」三个字可信；
- **失败原因 + 建议**：把错误翻译成「原因 + 重试/接管/跳过」，而不是「出错了」。

## 2. 调研结论（摘要）

参考：[AI Agent UI Design Patterns](https://brainy.ink/paper/ai-agent-ui-design-patterns) 的 7 个模式：任务框架、自主度、计划面、进度流、确认门、错误恢复、交接。

可直接落地的四条：

1. **进度流要结构化**：每步一行（动作/目标/结果/耗时），不要把模型思考塞进卡片；卡片负责「看得见」，对话负责「说清楚」。
2. **背景任务要有存在感但不打扰**：默认可见、可折叠、可暂停；「后台执行 · 不影响你」是状态，不是文案装饰。
3. **错误恢复是产品的一半**：失败必须带「为什么 + 能怎么办」，且保留现场（上一步截图、可重试、可接管）。
4. **确认门分级**：可撤销 / 有破坏性 / 灾难性三档；普通步骤不打断，只有改设置、删除、发送这类才弹确认。

同类做法：ChatGPT Operator 是“受监督浏览器”，动作日志在聊天面板、可暂停接管；Claude Code 是“透明终端”；Devin 给工作台全景；Cursor 是 ambien presence。我们取 **Operator（可看可接管）+ Claude Code（每步一行）** 的组合。

## 3. 卡片解剖

```text
┌──────────────────────────────────────────────────────────────┐
│ ● 正在操作 · 第 4/5 步            8.1s   [后台执行·不影响你]  ▾ │
│   目标：系统设置 › 外观 › 对比度                                │
│   ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░  （分段进度：5 段）              │
├──────────────────────────────────────────────────────────────┤
│ ① 打开「系统设置」  已完成   前台激活 0.9s        [缩略图]     │
│ ② 点击「显示器」侧边栏  已完成  AXPress·后台 2.4s [缩略图]     │
│ ③ 截图显示器排列  已完成   长边 1280·JPEG q80 0.4s [缩略图]    │
│ ④ 把对比度改为「增强」 进行中  需要你确认                       │
│    ┌ 需要确认：会修改「对比度」设置（可撤销）。确认继续？      │
│ ⑤ 拖拽 hello.txt 到下载窗口  待执行  后台拖拽                  │
├──────────────────────────────────────────────────────────────┤
│ 第 4 步等你确认            [继续并修改]  [跳过这步]            │
└──────────────────────────────────────────────────────────────┘
```

**每个工具调用占一行**（不是每一步都单独一张大卡），但整轮任务共享一张「活动卡片」作为容器。卡片本身随工具流累积，完成后折叠成摘要：「4 步 · 6.8s · 2 张截图」。

### 状态机

`运行中` → `等待确认`／`已冻结（失败/等待用户）` → `成功`／`跳过`／`失败`／`取消`。
失败后重试：同一行回到 `运行中`，计数 n 不变、重试次数 +1（显示 `重试 1/2`）。

## 4. 数据契约

### P0（纯客户端，可先上）

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| 第 n/N 步 | 同一轮动作计数；有 plan 时取 `plan_create` 的 steps 总数 | N 不可知时显示 `第 n 步` |
| 目标 App/窗口/控件 | 工具参数 + 输出里的 `frontmost_app`／AX 标题 | 缺失时退化为「窗口截图」 |
| 耗时 | block 生命周期（call 开始→result 结束） | `tool.call` 与 `tool.call.result` 的时间差 |
| 缩略截图 | 结果里 image 附件 | 取最后一张，或每步各一张（可拍板） |
| 失败原因/建议 | `actionEffect`／`note`／`error` 文本 + 现有 hint | `suspected_noop` → 「画面没有变化」+「目标可能被遮挡，先置顶再重试」 |
| 确认门 | 参数里的危险动作词 + 现有 guard | 规则与 host guard 同源，客户端只负责展示 |

### P1（宿主补字段，不必做但更稳）

动作类工具输出增加可选 `ui` 对象：

```json
{ "target": { "app": "系统设置", "window": "外观", "element": "对比度" },
  "durationMs": 2400,
  "effect": "confirmed",
  "step": { "index": 4, "total": 5 },
  "hint": "目标窗口可能被其他窗口挡住" }
```

全部可选、不破坏旧 schema；客户端优先读 `ui`，缺失时回退 P0 解析。P1 的改动由 199 项测试兜住。

## 5. 交互细节

- **默认展开、可折叠**：活动中的卡片展开；完成后自动折叠成一行摘要（4 步 · 6.8s · 2 张截图）。
- **缩略图**：每步一张 64×40 静态图 + 按动作类型叠加的轻量动画；点击放大（灯箱），支持前后切换。P0 实现时默认显示每步缩略图，避免长卡片过长可折叠为「查看全部」。
- **确认门**：只出现在可撤销/破坏性动作前；文案写清「改什么、可否撤销、超时怎么办」；按钮「继续并修改 / 跳过这步」；底部状态栏与卡片同步。
- **失败**：行内红条 + 原因/建议 + 三个动作「重试这一步 / 我来接管 / 查看上一步截图」；「重试」需带原因（如“重试并置顶目标”），不能空重试。
- **接管**：点击后取消后台执行，把控制权交还用户；卡片显示「等你操作」并停止计时。
- **后台徽标**：默认显示「后台执行 · 不影响你」，前台操作时显示「前台执行」；这是信任感的来源，不藏。
- **桌面 HUD**：右下角常驻小窗同步 n/N、目标、进度与干预徽标（`正在操作/需要你确认/需要处理/你接管中/已完成`）；不抢焦点，点「回到卡片」跳回会话（详情见 §9.1）。
- **缩略图动画**：每步缩略图按动作类型叠加轻量动画（点击呼吸框、截图闪光、拖拽路径流动），静态截图不变，`prefers-reduced-motion` 关闭（见 §9.2）。
- **无障碍**：状态不只靠颜色（点+文字+图标）；按钮可 Tab 聚焦；缩略图有 alt（「显示器设置截图，2026-11-01」）。
- **滚动**：卡片超过视口时内部滚动，不抢聊天滚动；键盘可折叠/展开。

## 6. 落地阶段

| 阶段 | 范围 | 风险 |
| --- | --- | --- |
| P0（1–2 天） | 客户端：活动卡片容器 + n/N + 每步耗时 + 缩略图取 image 附件 + 失败原因/建议（复用现有 note/actionEffect）+ 确认门展示 | 低：只改 `client/client.js`，不碰宿主 |
| P1（2–3 天） | 宿主补可选 `ui` 字段；连续动作折叠成一张卡；完成后折叠摘要 | 中：动 wire schema，199 项测试兜底 |
| P2（可选） | 暂停/接管（cua-driver 已支持前台接管语义）；卡片内直接确认破坏性动作（对接 guard） | 中：涉及执行控制 |

先做 P0，不碰宿主组合层与 wire 协议，风险最小。

## 7. 已拍板（m08916）

| 问题 | 结论 |
| --- | --- |
| 方案 A 还是 B | **A 活动卡片**（B 只留作对照切换） |
| 默认展开还是折叠 | **运行中展开；完成后折叠成一行摘要** |
| 缩略图数量 | **每步一张**；默认只看最后一张 + 点击灯箱看全部/前后切换 |
| 后台徽标 | **要标**，且区分「后台执行 · 不影响你」（AXPress/CGEvent 后台投递、不抢焦点）与「前台执行 · 短暂占用」（激活 App、原生菜单/部分 Electron 输入）；HUD 上的「需要你确认/需要处理/等你操作」是干预提示，不是执行模式 |

| 确认门范围 | **只对改设置 / 删除 / 发送**这类可撤销或破坏性动作；普通点击、截图、读取不打断。所有插件执行都会出现卡片 |

## 9. m08916 追加：桌面 HUD + 动画（demo 已实现，P2 待评估）

### 9.1 桌面常驻 HUD（像 dsh-pet 那样的小窗）

诉求：不打开会话也能看到「执行到哪、要不要我干预」。demo 里在右下角做了概念预览，状态四种：

| 状态 | 显示 | 触发 |
| --- | --- | --- |
| 运行中 | `正在操作 · 第 n/N 步` + 目标 + 分段进度 + 白点 | 任意工具执行 |
| 需要你确认 / 需要处理 | 进度段变橙 + 徽标 `需要你确认`／`需要处理` | 确认门 / 失败 |
| 你接管中 | `等你操作` + 底栏「我操作完了，继续」 | 点「我来接管」 |
| 已完成 | `已完成 · n/N 步` + 摘要 | 成功/结束 |

可行性评估（P2）：HUD 本质是一个**始终置顶、不抢焦点的小窗口**。
- 方案 A：客户端注入 `position:fixed` 浮层——零依赖，但只在 DSH 窗口内可见，切到别的 App 就看不到；
- 方案 B：宿主/插件再挂一个无边框置顶小窗（`dsh-pet` 已经证明了 Electron 置顶窗可行）——跨 App 可见，但需要额外窗口进程与 IPC，属于宿主层改动；
- 建议：P0 先在客户端做浮层（真源是同一份卡片状态，后续搬到置顶窗不用重做 UI）；P2 再评估独立窗口。

### 9.2 缩略图动画（按动作类型，已按 m09080 收敛）

静态截图不够「活」，按动作类型叠一层轻量动画，让用户不用读文字也知道发生了什么。**原则：不做闪烁**——没有无限扫光、没有明暗脉冲。

**步骤推进是主秀场，用「一击式」高冲击动效（播放一次，不循环）**：

- 进度条：当前段**从左充能**（scaleX + 亮度回落 0.55s），同时一道高光**扫过一次**；刚完成的段亮度回弹；
- 步骤行：当前行一条**暖色光带横扫**（0.85s）；序号徽章**弹跳 overshoot**；完成行的对勾**描边画出**（stroke-dashoffset）；
- 卡片标题 / HUD 的「第 n/N 步」：数字**上滑替换**（0.34s）；
- 缩略图：`ax_press` 目标框**慢呼吸**（4s 一轮，唯一循环动效）；截图 = 静态图 + 完成勾；拖拽 = 静态路径 + 起终点；
- 不做重复闪烁：没有无限扫光、没有明暗脉冲、没有逐条淡入。

动画只叠在缩略图上，不重做截图本身；`prefers-reduced-motion` 下全部关闭。

### 9.3 其他动效（已收敛）

一次性动效：卡片入场、确认门滑入、失败抖动（420ms 一次）、灯箱、loading 转圈；步骤推进用上面的一击式组合（0.34–0.9s）。**不做**：无限扫光/无限脉冲/整行淡入（状态更新会重建节点，是「一闪一闪」的来源）。原则：单次播放、不阻塞点击、同一元素不重复播放；`prefers-reduced-motion` 全部关闭。
