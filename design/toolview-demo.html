设计说明

为什么是「活动卡片」而不是「一行日志」

Agent 的 UI 是控制面，不是聊天窗。研究里被反复验证的 7 个模式：任务框架、自主度、计划面、进度流、确认门、错误恢复、交接。卡片至少同时承担「进度流 + 确认门 + 错误恢复」三件。

  • 每步一行：只放动作、目标、耗时、结果，不塞模型思考。
  • 目标显式化：App › 窗口 › 控件，用户一眼能判断“点得对不对”。
  • 缩略图：截图即证据，比“已点击”三个字可信。
  • 失败给下一步：原因 + 建议动作（重试/置顶/接管），而不是一句“出错了”。

参考：AI Agent UI Design Patterns（progress stream 必须结构化；error recovery 是产品的一半）。

数据从哪来（客户端可先行）

P0 纯客户端：数量 n/N 用同一轮动作计数（有 plan 时取 plan 总步数）；耗时用 block 生命周期时间；缩略图直接取工具结果里的 image 附件；失败原因沿用现有 actionEffect/note/error 文本。

P1 宿主补字段：动作类工具输出增加可选 ui 对象：

ui:{ target:{app,window,element}, durationMs, effect, step:{index,total}, hint }

全部可选，不破坏旧 schema；客户端优先读 ui，缺失时回退 P0 解析。

滚动落地

  • P0（1–2 天）：动作工具注册自定义卡片；缩略图 + 每步耗时 + n/N 计数 + 失败态与建议按钮（重试由模型重新调用，不新增协议）。
  • P1（2–3 天）：宿主补 ui 字段；连续动作折叠为一张活动卡；完成后折叠成摘要行（4 步 · 6.8s · 2 张截图）。
  • P2（可选）：暂停/接管（cua-driver 已支持前台接管语义）、多任务并排、卡片内直接确认破坏性动作（对接 guard）。

取舍：先做客户端，不碰宿主组合层与 wire 协议，风险最小；P1 再动 host，改动被 199 项测试兜住。

调研速记

同类产品的做法

  • ChatGPT Operator：受监督浏览器，动作日志在会话里，可暂停/接管；支付等动作先暂停确认。
  • Claude Code：终端即界面，每个工具调用、diff 实时流式输出；计划以 markdown 呈现。
  • Devin：工作台全景（浏览器/终端/编辑器），用户可从任一层接管。
  • Cursor：小事隐形、大事出计划，按任务规模校准存在感。

可以借的 5 个细节

  • 「开始 / 关键节点 / 结果」三张截图随进度出现，带一句 caption。
  • 破坏性动作卡片单列，不和普通步骤混排；可加一条打字确认。
  • 暂停按钮常驻，不藏在设置里。
  • 失败后保留现场：重试不清空前面的成功步骤。
  • 完成态折叠成一行摘要，别占着屏幕。

需要你拍板的点

  • 方案 A 还是 B？（推荐 A，B 作为小屏/低干扰模式）
  • 卡片默认展开还是折叠？
  • 缩略图默认显示几张（建议只显示最后一张 + 手动展开）？
  • 「后台执行」要不要带明显的 agent cursor 徽标？
  • 失败时的「我来接管」是跳到前台接管，还是只给指引？
